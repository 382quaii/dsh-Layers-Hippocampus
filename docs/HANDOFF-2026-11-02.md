## 问题 1（P0）：写入吞吐 ~100 条/秒，bulk 场景不可用

实测：

```
1000 × memory.remember → 9788 ms ≈ 102 条/秒
日志体积 495 KB，≈ 413 B/事件
```

**这与 `bulkIngest` 无关**：`bulkIngest` 只是每 50 条顺序 `await remember`，没有批量化写入；`WriteQueue` 模块存在但**未接入 remember 路径**。

排查建议（文件定位）：

1. `src/memory.js` 的 `remember()`：每条约 `assertWriteBudget() → logStore.append → indexManager.applyRecords → refreshBriefing()`，其中 `refreshBriefing()` 每写一条都重算是明显浪费。
2. `src/log/logStore.js`：`append` 附近多处 `writeJsonAtomic(...LOG_MANIFEST)`（L96/159/185/285）——如果每条记录都原子重写 manifest，这就是主要成本（建议：manifest 只在 rotation/close 时写，或 append 后延迟合并）。
3. 建议方案：
   - `remember` 拆成 `stage()`（验重、构造记录、内存缓冲）+ `commitMany()`（一次 append + 一次 index apply + 一次 briefing 刷新）；
   - `bulkIngest` 直接走 `commitMany`（真正每 50 条一次 IO）；
   - `refreshBriefing` 改为 dirty 标记 + 定时/按需刷新；
   - 验收：1000 条 ≤ 1000ms（≈1000/s），索引可见性不变。

**不要破坏**：幂等（content_hash/occurrence_index）、tombstone 过滤、A/B 索引代际。

## 问题 2（P0）：`deep_raw` 大分片下查不到最新记录（正确性 bug）

实测（单分片 10,000 行，`raw/2026-..jsonl`）：

```
查 "raw line 9999"（最新） → hits 0, truncated true, scannedTurns 5000, maxScanTurns 5000
查 "raw line 1 "（较早）   → 有命中
hash 精确恢复             → hits 1, 内容一致 ✅
```

根因：`src/rawStore.js` L307 `maxTurns = Math.min(5000, config.maxScanTurns ?? 5000)`，扫描 `for await (line of lines)` 从**文件头**开始，达到 5000 条即 `truncated` 停止——最新的 5000 条永远扫不到。`maxScanTurns` 也没有进入 config，UI 无法调。

建议方案：

1. 分片内**从尾部倒序**扫描（读文件后按行倒序，或分块从尾部读），保证“最近优先”；
2. `maxScanTurns` 加入 `config.raw.maxScanTurns`（默认 5000，范围 500–50000），UI 可调；
3. 验收：10k 分片查最新 1 条能命中且 `truncated:false`（或扫描到即停）；查 1 万条以外的旧记录时明确 `truncated:true` 且 `notes` 说明。

**不要破坏**：四字段 schema、tombstone 跳过、read-side 脱敏、token 预算提示、hash 恢复。
